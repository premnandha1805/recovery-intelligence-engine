# Day 4 Causal-Uplift Machine Learning Pipeline

## Final Technical & Research Report

## 1. Overview

The purpose of the Day 4 ML layer in the **Recovery Intelligence Engine** is to estimate potential payment recovery outcomes for all candidate actions and deploy a net-financial-value maximizing decision policy (`CausalUpliftPolicy`).

The system models four possible recovery interventions:
- `WAIT`: Passive monitoring (zero direct intervention cost).
- `RETRY`: Automated payment retry transaction.
- `RETRY_NUDGE`: Automated retry combined with dunning notification (SMS/email).
- `ESCALATE`: High-touch intervention channel (manual agent or support ticket).

### Architectural Context & Day 3/4 Boundary

Day 3 established the core baseline infrastructure:
- Stateful V2 payment simulation engine (`simulator/`)
- Observable payment and customer state (`payment_scenarios.csv`)
- Simulator hidden ground truth (`ground_truth.csv`)
- Four baseline policies (`WaitPolicy`, `AlwaysRetryPolicy`, `AlwaysNudgePolicy`, `RuleBasedPolicy`)
- Policy evaluation and reporting pipeline (`evaluation/evaluator.py`, `evaluation/report.py`)

Day 4 adds the Machine Learning and Causal Inference layer (`ml/`) on top of Day 3 **without modifying any frozen Day 3 policy code, baseline files, or evaluation logic**.

## 2. The Confounding Problem

### 2.1 Treatment-Selection Bias in Observational Logs

In observational payment data generated by heuristic rules (such as Day 3's `RuleBasedPolicy`), treatment assignment is non-random:

$$T \not\!\perp\!\!\!\perp (Y(1), Y(0)) \mid X$$

`RuleBasedPolicy` assigns interventions based on customer risk metrics (e.g. `dynamic_success_rate`, `consecutive_failed_cycles`). Observing a high recovery rate under `RETRY` does not establish that `RETRY` *caused* recovery—the targeted payments may have had higher baseline recovery rates. Naive supervised learning on heuristic logs learns the policy's assignment rules rather than counterfactual treatment effects.

### 2.2 The Day 4B Randomized Logging Solution

To eliminate treatment-selection bias within the experimental training setup, Day 4B generates a dedicated training dataset (`ml/data/causal_training_data.csv`) where treatment $T$ is assigned **uniformly at random** across all four treatment arms using a dedicated RNG:

$$T \sim \text{Uniform}(\{\text{WAIT}, \text{RETRY}, \text{RETRY\_NUDGE}, \text{ESCALATE}\})$$

Because $T \perp\!\!\!\perp X$ by construction, observational conditional expectations equal counterfactual potential outcomes:

$$E[Y \mid X, T = a] = E[Y(a) \mid X]$$

> **Methodological Nuance**: Uniform randomization removes the treatment-assignment confounding created by `RuleBasedPolicy` within this experimental training setup. It does not automatically guarantee unconfoundedness in unobserved real-world environments, but it provides a clean, unconfounded basis for training the causal estimator.

## 4. Feature Contract and Leakage Firewall — 4C/4D

### 4.1 Feature Contract (`ml/dataset.py`)

The dataset contract defines explicit feature constants to prevent schema drift:

```text
Observable Features (X):
  amount
  attempt_number
  dynamic_success_rate
  cumulative_failures
  consecutive_failed_cycles
  notification_engagement_score
  contact_response_score
  payment_method
  failure_reason

Treatment (T):
  assigned_T

Outcome (Y):
  realized_Y  (strictly binary 0/1, never a probability)
```

`load_causal_dataset()` loads `ml/data/causal_training_data.csv` and returns `(X, T, Y)` as three separate objects. `payment_id` is excluded from $X$.

### 4.2 Leakage Firewall (`ml/firewall.py`)

`assert_no_leakage(df)` provides a second, independent guard invoked before any training or prediction step.

- **Forbidden-Prefix Guard**: Rejects any column name starting with:
  `p_success`, `hidden_`, `natural_recovery`, `retry_success_probability`, `nudge_success_probability`, `escalation_success_probability`, `expected_recovery`, `expected_net_value`.
- **Outcome-Token Guard**: Rejects any column containing substring `"outcome"` (case-insensitive), EXCEPT for the exact declared `OUTCOME_COLUMN` (`realized_Y`).
- **Rationale**: Hidden simulator probabilities or future outcome tokens entering $X$ would create data leakage and artificially inflate model performance. The firewall fails loudly (`LeakageError`) rather than silently allowing suspiciously good results.

## 6. T-Learner Architecture — 4F

- **Module**: `ml/t_learner.py`

### Architecture Overview

```text
Observable X
    │
    ├─► WAIT (T == "WAIT") ────────► Logistic Regression Pipeline ─► Ŷ_WAIT
    │
    ├─► RETRY (T == "RETRY") ──────► Logistic Regression Pipeline ─► Ŷ_RETRY
    │
    ├─► RETRY_NUDGE (T == "NUDGE") ─► Logistic Regression Pipeline ─► Ŷ_RETRY_NUDGE
    │
    └─► ESCALATE (T == "ESCALATE") ─► Logistic Regression Pipeline ─► Ŷ_ESCALATE
```

Each arm model is trained **only on rows where `assigned_T == arm`**.

### Model & Preprocessing Pipeline
- **Base Classifier**: `LogisticRegression(max_iter=1000, solver="lbfgs", random_state=42)`
- **Preprocessing Pipeline**:
  - `StandardScaler` for numerical features.
  - `OneHotEncoder(handle_unknown="ignore")` for categorical features (`payment_method`, `failure_reason`).
- **Rationale**: Logistic regression was selected because it is interpretable, defensible, mathematically transparent, and provides a strong baseline for research evaluation.
- **Swappable Architecture**: Implemented via `make_classifier()` factory function, allowing future replacement with tree-based gradient boosting without modifying the T-Learner architecture. Gradient boosting was **not** built in Day 4.
- **Firewall Integration**: `assert_no_leakage(training_frame)` is called before fitting each arm.

## 8. Treatment Effects — 4G

- **Module**: `ml/treatment_effects.py`

### Definitions
Conditional Average Treatment Effects (CATE) relative to `WAIT` (control):

$$\tau_{\text{retry}}(X) = \hat{Y}_{\text{RETRY}}(X) - \hat{Y}_{\text{WAIT}}(X)$$

$$\tau_{\text{nudge}}(X) = \hat{Y}_{\text{RETRY\_NUDGE}}(X) - \hat{Y}_{\text{WAIT}}(X)$$

$$\tau_{\text{escalate}}(X) = \hat{Y}_{\text{ESCALATE}}(X) - \hat{Y}_{\text{WAIT}}(X)$$

## 10. CausalUpliftPolicy — 4I

- **Module**: `ml/decision.py`
- **Class**: `CausalUpliftPolicy(Policy)` (subclasses `policy/base.py`)

### Implemented Decision Formula
For a payment record with observable features $X$ and payment amount $A$:

$$\text{net\_val}(a) = \left( \hat{P}(Y=1 \mid X, T=a) \times A \right) - \text{ACTION\_COSTS}[a]$$

$$\pi^*(X) = \arg\max_{a \in \{\text{WAIT}, \text{RETRY}, \text{RETRY\_NUDGE}, \text{ESCALATE}\}} \text{net\_val}(a)$$

### Action Cost Schedule (`policy/cost_config.py`)
- `Action.WAIT`: **INR 0.0**
- `Action.RETRY`: **INR 5.0**
- `Action.RETRY_NUDGE`: **INR 15.0**
- `Action.ESCALATE`: **INR 250.0**

`Action.WAIT` (cost 0.0) is a valid candidate and is able to win whenever the expected recovery from active interventions does not exceed intervention costs.

## 13. Why the Causal Policy Performs Better in This Simulation

`CausalUpliftPolicy` primarily allocates actions between `RETRY` (~65–66%) and `RETRY_NUDGE` (~31–33%), while restricting `ESCALATE` to $<0.15\%$ of payments.

`RuleBasedPolicy` assigns approximately 18–19% of all payments to `ESCALATE`. `ESCALATE` carries a high intervention cost (INR 250).

Because `CausalUpliftPolicy` explicitly evaluates expected net financial recovery ($\hat{Y}(a) \times A - \text{cost}(a)$), it reserves `ESCALATE` strictly for high-amount accounts where incremental recovery exceeds INR 250. This drastically cuts intervention expenditure (INR 248K vs INR 1.68M) while achieving higher gross recovery (27.05% vs 25.31%).

> **Research Caution**: This explains the observed result in the current simulator/evaluation environment. It does **not** prove that the exact same numerical improvement will occur in production.

## 14. What Could Go Wrong in Production?

### T-Learner limitation
This is a T-Learner, **not** a doubly robust estimator. Separate outcome models are fitted per treatment arm, and treatment effects are derived from differences between predicted potential outcomes. Model misspecification in any arm model can directly distort uplift estimates.

### Fixed action costs
The policy assumes action costs are fixed and known (`WAIT` = 0, `RETRY` = 5, `RETRY_NUDGE` = 15, `ESCALATE` = 250). In production, intervention costs may vary dynamically due to gateway fees, vendor pricing, or operational overhead. Changing costs alter optimal decision boundaries even if ML models remain unchanged.

### Weak arm models
Current 4F results found **no weak arm** (AUCs: ESCALATE 0.8507, RETRY 0.8080, RETRY_NUDGE 0.8084, WAIT 0.8606). No arm was identified as weak in the current experiment. However, arm performance must be continuously monitored because production distribution shifts can degrade specific arms selectively.

### Distribution shift
Production customer behavior may drift away from the training distribution, reducing prediction accuracy.

### Positivity / overlap
Randomized training logging provides treatment overlap by construction, but real production policies might not. Sparse feature regions with missing treatment arms make treatment-effect estimation unreliable.

### Simulator-to-production gap
Ground truth comes from synthetic simulation. Agreement with simulator ground truth is a necessary validation step but is not equivalent to proving production causal effectiveness.

### Objective mismatch
The current objective optimizes net financial recovery ($\text{gross recovery} - \text{cost}$). Production decisions must also consider customer experience, churn, support burden, brand reputation, and long-term customer lifetime value (LTV). Immediate net recovery may not equal total business value.
